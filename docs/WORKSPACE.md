# Workspace guide

## Principles

- **One folder, one application.** Each of the 25 projects lives in a top-level folder and is a complete application with a desktop dashboard, a terminal UI and a CLI over one service layer.
- **No cross-folder imports.** Shared code is copied from `templates/<language>/` when a project is created. A folder can be split into its own repository without code changes.
- **Truthful status.** `scripts/projects.tsv` is the registry. The README table is generated from it and CI fails if the table, the registry and the folders disagree.
- **Path-filtered CI.** Every project and template has its own workflow with a path filter, generated by `scripts/gen-workflows.sh`. A change to one project runs only that project's jobs.

## Registry

`scripts/projects.tsv` is a tab-separated file with one row per project:

| Column | Meaning |
|---|---|
| `number` | Position in the project table, 1 to 25 |
| `folder` | Top-level folder and future repository name |
| `app` | Display name |
| `language` | Primary language: `go`, `rust` or `cpp` |
| `status` | `Not started`, `In progress` or `Complete` |
| `tagline` | Short phrase used as the one-line description in the table |
| `topics` | Exactly seven GitHub topics, comma separated |
| `icon_concept` | Concept for the original application icon |
| `description` | GitHub description, one sentence of about 200 to 280 characters |

`Not started` is valid only while the folder does not exist. `In progress` and `Complete` require the folder.

## Scripts

Every script starts with `#!/usr/bin/env bash` and `set -euo pipefail`, supports `--help`, and supports `--dry-run` when it changes something.

| Script | Purpose |
|---|---|
| `scripts/list-projects.sh` | Print the registry as a table, Markdown, TSV or folder list |
| `scripts/check-all.sh [target...]` | Run `make check` in every template and project that exists, or in the given targets |
| `scripts/gen-workflows.sh` | Render `templates/workflows/` into `.github/workflows/`; `--check` verifies, `--standalone` renders for a split repository |
| `scripts/new-project.sh <name> <go\|rust\|cpp>` | Create a project folder from its language template with metadata from the registry |
| `scripts/split-project.sh <project>` | Extract a project with history into a standalone repository |
| `scripts/init-main.sh` | Create the local branch `main` as one commit `chore: initial public release` with the files of the current commit |
| `scripts/publish-github.sh` | Create and publish the public `workspace` repository with `gh` |
| `scripts/sync-readme.sh` | Refresh the project table in `README.md` |
| `scripts/verify-repo.sh [check...]` | Repository checks, described below |
| `scripts/install-shell-tools.sh` | Install the pinned shellcheck, shfmt and bats |

`scripts/lib.sh` holds the shared functions and `scripts/find-comments.awk` is the comment scanner. Tests live in `scripts/tests/` and run with bats against a temporary workspace, a fake `gh` and a local bare remote.

## Repository checks

`make check` at the root runs:

1. `shellcheck` on every script and bats file
2. `shfmt -d` on the same files
3. `bats scripts/tests`
4. `scripts/verify-repo.sh`, which runs:

| Check | What fails it |
|---|---|
| `registry` | Not exactly 25 rows, a wrong language count (14 Go, 8 Rust, 3 C++), an invalid status, a status that contradicts the folder, a topic count other than seven, a description far outside 200 to 280 characters |
| `files` | A missing root file, or a template or project folder without one of the required files, directories, Makefile targets or README sections |
| `emails` | Any email address in a tracked or untracked, non-ignored file |
| `comments` | A comment in a Go, Rust, C++, SQL or Bash source file outside `testdata/`, `third_party/` and `vendor/` |
| `workflows` | `.github/workflows` differs from what `scripts/gen-workflows.sh` generates |
| `readme` | The project table in `README.md` differs from the registry |

The comment scanner understands string, character and raw-string literals of each language, Bash here-documents and quoting, and allows only the shebang line in Bash and `//go:` directives at the start of a line in Go.

## Workflows

Workflow files in `.github/workflows/` are generated. Edit the template in `templates/workflows/` and run `scripts/gen-workflows.sh`.

| Generated file | Source | Trigger |
|---|---|---|
| `root-ci.yml` | `root-ci.yml` | Every push and pull request |
| `template-<language>-ci.yml` | `<language>-ci.yml` | Changes under `templates/<language>/` |
| `<project>-ci.yml` | `<language>-ci.yml` | Changes under `<project>/` |
| `<project>-release.yml` | `<language>-release.yml` | Tags matching `<project>/v*` |

Templates use the tokens `__NAME__`, `__APP_NAME__`, `__WORKDIR__`, `__PATH_FILTER__`, `__TAG_PATTERN__` and `__SELF__`. For a standalone repository the same templates are rendered with the working directory `.` and the tag pattern `v*`.

Third-party actions are pinned to commit hashes:

| Action | Version | Commit |
|---|---|---|
| `actions/checkout` | v7.0.1 | `3d3c42e5aac5ba805825da76410c181273ba90b1` |
| `actions/setup-go` | v7.0.0 | `b7ad1dad31e06c5925ef5d2fc7ad053ef454303e` |
| `actions/upload-artifact` | v7.0.2 | `cf430e030ddbb5b0abf93d22962f4752f3646cd9` |
| `actions/download-artifact` | v8.0.2 | `9000827ccba6bdab643e8b6fd33ac0654aef8333` |

## Commit and identity rules

- Conventional Commits with the project folder as the scope, see `CONTRIBUTING.md`.
- Commits use a GitHub noreply identity. `scripts/publish-github.sh` refuses to publish when `git config user.email` is not a noreply address or when history contains another address.
- No email address appears in any file.
